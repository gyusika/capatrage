# Capacity Arbitrage

과수요가 확인된 시장에 공급하고, 그 공급수단을 경매에서 싸게 확보한다.

```
수요 데이터 → 과수요 지역 발견 → 예상 매출 → 필요한 물건 조건 → 경매 검색 → 권리/인허가 검토 → 낙찰가 결정
└────────────────── 지금 구현된 범위 ──────────────────┘
```

**원칙: 실측값만 쓴다.** 리뷰 증분이나 환산으로 예약을 추정하지 않는다.

## 파이프라인

```bash
npm run sitemap       # 공간 14,090개 + 리뷰 20,000건 열거 (~10초)
npm run crawl         # 상세 전수 (~78분, 3 req/s)
npm run load          # 공간·상품·태그 적재
npm run booking       # 실제 예약 현황 (~65분, 2 req/s)
npm run load:booking  # 예약 적재
npm run compute       # 영업시간 판정 + 예약률 계산
npm run daily         # 위 전부 순서대로
npm run web           # 대시보드 (localhost:3000)
```

크롤은 중단해도 `data/*/{date}/done.txt` 기준으로 이어서 받는다.

## 자동 수집 (GitHub Actions)

`.github/workflows/daily.yml` 이 매일 04:00 KST 에 돈다. 두 잡으로 나뉜다.

| 잡 | 내용 | 소요 |
|---|---|---|
| `crawl` | sitemap + 상세 전수 + 적재 → 스냅샷을 아티팩트로 넘김 | ~80분 |
| `booking` | 예약 관측(서울) + 적재 + 예약률 + 매출 | ~3시간 |

**왜 매일이어야 하는가.** 상품의 51%(10,355개 중 5,324개)가 예약 마감 설정 때문에
D+2 부터만 달력에 열린다. 그 업체의 D+0/D+1 예약 현황은 **이틀 전에 봐두지 않으면
영원히 관측할 수 없다.** 하루 거르면 그날 마감된 업체들의 근접일이 통째로 빈다.

**왜 Vercel/Supabase 가 아닌가.** 예약 수집이 서울만 해도 약 3시간이다.
Vercel Function 도 Supabase Edge Function 도 실행시간 한도가 800초라 담을 수 없다.

관측일은 `RUN_DATE` 로 고정한다. `today()` 가 UTC 기준이라 새벽 실행 시 KST 와 하루
어긋나고, 잡이 둘로 나뉘면 경계에서 날짜가 갈린다. 잡이 실패하면 `done.txt` 를
캐시에서 복원해 이어받으므로 재실행이 처음부터 다시 받지 않는다.

요청률은 로컬과 동일하다(크롤 3, 예약 2 req/s). `concurrency` 로 이전 실행과 겹치지
않게 막아 상대 서버가 받는 부하가 늘지 않게 했다.

필요한 secret 은 `DATABASE_URL` 하나다.

## 데이터 소스

### 공간 정보 — 스페이스클라우드 (robots 준수)

| 경로 | 상태 | 용도 |
|---|---|---|
| `www.spacecloud.kr/sitemap.xml` | 허용 | 공간 14,090개 + 리뷰 20,000건 열거 |
| `www.spacecloud.kr/space/{id}` | 허용 | 상세 (가격·평수·정원·좌표·휴무) |
| `www.spacecloud.kr/search*` | **Disallow** | 쓰지 않음. 열거는 sitemap 으로만 |

상세 페이지가 Nuxt SSR 이라 `window.__NUXT__` 안에 API 응답이 통째로 들어있다.

### 예약 현황 — `api.spacecloud.kr` (robots 미준수, 사용자 승인)

```
GET /products/{product_id}/prices?reservation_type_id=&year=&month=
```

익명으로 200. 한 번 호출에 약 36~43일치 시간별 `available` 이 온다.
**이 호스트는 robots.txt 에서 크롤러에 disallow 다.** 실측 예약 데이터를 얻을 다른 경로가
없어서 사용자가 명시적으로 승인하고 진행한다. 초당 2건으로 제한한다.

검토했다가 배제한 경로:
- 스페이스클라우드 `/reserve/` — robots disallow
- 아워플레이스 — 사이트 본체는 `Claude-User` 에 전체 허용이지만 예약 API 가 별도 호스트(`api2`)이고 거긴 예외 없음
- 네이버 예약 — 전면 차단

## 예약률을 계산할 때 반드시 걸러야 하는 두 가지

실측하다 잡은 오류다. 안 거르면 숫자가 통째로 틀린다.

**1. 휴무 시간이 "예약됨"으로 들어온다.**
API 의 `available=false` 는 예약과 영업시간 밖을 구분하지 않는다. `break_times` 가
24시~9시인 공간은 0~8시가 매일 false 다. 실측하니 공간당 막힌 5.18시간 중 **4.60시간이 휴무**였다.
이걸 예약으로 세면 예약률이 21.9% 로 나온다. 실제는 1.6% 다.

`break_times` 를 해석하는 대신 데이터에서 직접 판정한다 — 관측된 미래 날짜(14일 이상)에서
**한 번도 열린 적 없는 시각**은 영업시간 밖으로 본다. 35일 내내 같은 시각이 예약되는 경우는
사실상 없으므로 안전하다.

**2. 오늘(D+0)은 이미 지나간 시각이 막혀 있다.**
예약이 아니다. `target_date > observed_date` 로 제외한다. 안 빼면 D+0 이 65.6% 로 튄다.

## 매출을 계산할 때 반드시 걸러야 하는 세 가지

예약률 쪽 함정(휴무·D+0)과 별개로, 돈을 계산할 때 걸리는 것들이다.

**1. 슬롯 차단용 더미 가격이 섞여 있다.**
예약된 시각의 단가에 1,000,000 / 999,900 / 2,000,000 이 나온다. 사장이 그 시간대를
팔지 않으려고 넣는 값이다. 그대로 세면 시간당 100만원짜리 방이 288시간 예약된 것이 되어
월 매출 8억이 나온다.

절대 금액으로는 못 자른다. 정상 단가가 연습실 9천원 ~ 숙박 7만원으로 벌어져 있다.
그 상품 자신의 통상 단가(관측된 시간 단가의 중앙값) 대비 배수로 판정한다.
배수 분포가 이봉이라 경계가 데이터에서 나온다 — 5~10배 251시간, **10~20배 14시간(골짜기)**,
20배 이상 228시간(시간당 평균 163만원). 그래서 10배를 경계로 쓴다.

게시 단가를 기준선으로 쓰는 방법은 버렸다. "1,000원부터" 식 미끼 최저가가 흔해서
(라이트온 게시 1,000원 / 실제 32,500원) 정상 상품이 대량 오탐된다.

**2. 인원에 따라 요금이 달라지는데 예약 인원은 관측할 수 없다.**

```
요금 = 기본가(기준인원 person_ceiling 까지) + 초과인원 × extra_person_price
charging_per_person = 'Y' 인 상품은 기본가 자체가 1인당 단가다
```

시간제 예약타입 16,419개 중 **12,508개(76%)** 에 인원 추가금이 붙는다.
기준인원 중앙값 5명, 최대인원 12명, 추가금 5,000원/인, 기본가 20,000원.
만석이면 기본가의 p50 2.54배 · p75 4.33배 · p90 7.86배가 된다.

우리가 API 에서 보는 price 는 기본가다. 예약 인원은 어디에도 노출되지 않는다.
**그래서 매출을 값 하나로 내지 않고 구간으로 낸다.**

| | 뜻 |
|---|---|
| 하한 `rev_month_*` | 기준 인원까지 예약한 경우. 그 경우 오차 0인 실측값 |
| 상한 `rev_month_*_ceil` | 만석인 경우. 전부 실측 필드로 계산 |

평균 인원은 잡지 않는다. 정원은 수용 한계지 통상 이용 인원이 아니고, 인원 분포에 대한
근거가 하나도 없다. 용도가 경매 낙찰가 역산이라 과대추정이 직접 손실이기도 하다.

건당 추가금(`extra_per_hour = 'N'`)은 연속된 예약 시간을 한 건으로 보고 덩어리마다 한 번
붙인다. 서로 다른 사람의 인접 예약은 하나로 합쳐져 상한이 낮게 잡히는데, 상한이므로
보수적인 방향이다.

실측 결과 예약이 있는 곳의 80.4%에서 구간이 생기고, 상한/하한 배수 중앙값은 1.90배다.
업종차가 크다 — 연습실 1.52배, 회의실 1.81배, 파티룸 2.43배, 촬영스튜디오 2.80배.
연습실 숫자는 좁고 촬영스튜디오 숫자는 넓게 읽어야 한다.

**3. 같은 시간이 패키지로도 팔리고, 패키지가 더 싸다.**

상품 하나에 시간제(TIME)와 패키지(PKG) 예약타입이 같이 붙는다. 서울 기준 시간제 예약타입
10,373개, 패키지 4,961개이고 **4,027개 상품이 둘 다 갖고 있다.**

패키지 응답은 날짜마다 `packages[{shour, ehour, price}]` 를 준다. 시작·끝 시각과 가격이
전부 실측이다. 표본 10곳에서 같은 구간을 시간제로 살 때의 합계와 비교하면:

| 공간 | 패키지 | 패키지가 | 같은 구간 시간제 합계 | 비율 |
|---|---|---|---|---|
| 1602 | 종일 9–18 | 770,000 | 1,386,000 | 56% |
| 75993 | 새벽 0–6 | 15,000 | 26,000 | 58% |
| 64647 | 전시 10–18 | 253,000 | 440,000 | 58% |
| 63818 | 데이 9–18 | 190,000 | 261,000 | 73% |
| 30293 | 새벽 0–6 | 20,000 | 24,000 | 83% |

예약된 시간을 전부 시간제 단가로 곱하면 그만큼 과대계상된다. 인원 미상 때와 같은 방식으로
구간을 낸다 — **예약 덩어리가 패키지 창과 정확히 일치하면 하한을 패키지가로, 상한은
시간제 합계로** 잡는다. 새 가정이 아니라 실측 가격 두 개의 구간이다.

`available = false` 를 "팔렸다"로 읽으면 안 된다. 그 구간이 통째로 비어야 패키지가 열리는
구조라, 6시간 중 1시간만 시간제로 팔려도 닫힌다(공간 79796에서 확인 — 패키지 13–18이 닫힌
날의 그 구간 시간제 예약은 5시간 중 2시간). 그래서 판매 신호로 쓰지 않고 가격표로만 쓴다.

자정을 넘는 창(예: 올나잇 19–7)은 하루 단위 예약 덩어리와 맞출 수 없어 보정에서 뺀다.
09-07 부분 표본(102곳) 기준으로 예약 덩어리 4,548건 중 133건(2.9%)이 창과 정확히 일치했고,
그 133건은 전부 패키지가 더 쌌다 — 시간제 합계 10,757,000원이 패키지가로는 5,977,000원(−44%).
넓게 걸리지는 않지만 걸리는 곳에서는 하한이 절반 가까이 내려간다.

## 지역 단위

주소가 지번("서울특별시 강서구 가양동 449-4")과 도로명("서울 마포구 토정로17길 11")으로 섞여
들어오고(도로명 69%) 시도 표기도 "서울"/"서울특별시"/"서울시"가 뒤섞인다. 문자열 파싱으로는
동이 안 잡힌다.

대신 `cortar_no`(10자리 법정동코드)를 지역 키로 쓴다. **100% 채워져 있다.**
앞 2자리 = 시도, 앞 5자리 = 시군구, 10자리 = 법정동.
동 이름은 지번 주소에서만 나오므로 같은 코드를 쓰는 지번 주소에서 빌려 채운다.

## 대시보드 (`web/`)

Next.js + Supabase 직결. 탭 넷:

- **지도** — 원 크기=면적, 색=예약률
- **순위표** — 동×업종 예약률 중앙값 + p25~p75 분포 (p25 가 높아야 "평범한 업체도 팔리는" 시장)
- **시간대** — 요일×시간 히트맵 + 리드타임 곡선
- **공급 현황** — 전국 시군구×업종 공급·가격·면적

색은 파랑 한 색 순차 스케일. 데이터 없는 칸은 색이 아니라 사선으로 구분해
"0%"와 "모름"이 섞이지 않게 했다.
